# SEOImpuls — обязательный постраничный рабочий регламент

Статус: рабочий регламент на 2026-10-15. Производственный сервер и GitHub Pages не задействовать. Источники: main = исходный архив, white-seo-rebuild = новая версия. При расхождениях проверять фактическое состояние GitHub; CHATGPT_PROJECT_CONTEXT.md — актуальная точка восстановления. Этот файл — не доказательство того, что все проверки уже выполнены.

## 1. Последовательность этапов без перестановок

0. Базовый снимок: сопоставить URL на сервере с исходниками; до релиза получить GSC (3–6 мес, страницы/запросы, clicks/impressions/positions, indexing, manual actions), список внутренних/внешних ссылок и реальные HTTP-статусы. Без GSC помечать риски/переносы предварительными.
1. Закрыть старые направления EN: по одной странице убрать массовые backlinks, коммерческие tier/PBN, DR, автоматизированные сетки, старые soft/strategy-builder и партнёрский VPS-редирект из новой сборки. Отдельно устранить старые пункты меню, footer, breadcrumb, sitemap и ссылки на отключённые URL. Сохранить исходник в main. Правки 301/410 на продакшене пока НЕ выполнять.
2. Довести английские главную, /seo/, /services/ и каждую допустимую услугу, далее About, FAQ, Contact, статьи. Уже переписанные EN страницы повторно проверить: ранее конкурентные списки могли быть ориентировочными, а не фактическим Google top-10.
3. Провести самостоятельную русскую семантику и локализацию RU. Не копировать англоязычные поисковые интенты механически.
4. Провести самостоятельную испанскую семантику и локализацию ES по конкретному целевому рынку.
5. Общий SEO + visual + content QA всех языков, затем утверждение URL-миграции и релизного архива. Разрешение на публикацию — отдельный запрос владельца.
6. После релиза мониторинг 200/301/404/410, GSC indexing, показов/кликов, каноникалов и аналитики; не выдавать ранжирование за гарантированный результат.

## 2. Цикл для КАЖДОЙ страницы (только по одной странице или одному чётко ограниченному системному дефекту)

### А. Исходные данные и интент (до написания)
- Записать URL живого сайта, путь Hugo, все локали, исторический Title/H1, canonical, статус, ссылки и существующие CTA. Не заявлять live-проверку, если не было доступа.
- Выбрать один основной коммерческий/информационный/навигационный интент, первичный запрос и набор второстепенных. Проверить overlap с каждой близкой страницей, выбрать owning URL.
- Сделать реальный SERP audit: запрос, точные язык+страна/устройство+дата, первые 10 органических результатов без рекламы, фактические URL, типы страниц, ответ на интент, SERP features, пробелы и содержание, которое можно улучшить. Если выдача не получена/Google недоступен, пометить SERP_UNVERIFIED и не выдавать ориентировочные списки за реальный топ-10.
- Разграничить авторитетный факт, рекламу конкурента и наши неподтверждённые обещания. Не копировать чужой текст.

### Б. Архитектура и содержимое
- Сначала решить KEEP URL / SAME-INTENT 301 / RETIRE 404/410 / DRAFT PENDING REVIEW. Старые URLs и GSC показатели занести в docs/seo-url-migration-register.csv. Не применять 301 к неэквивалентной странице, не сбрасывать всё на главную.
- Для законной услуги: Title, один H1, description, slug/URL, содержание, фактическая методика, результаты и ограничения работы, честный CTA, FAQ лишь там где релевантно, уникальные внутренние ссылки.
- Не выдумывать цены, кейсы, число клиентов, сертификаты и гарантии. До подтверждения бизнес-предложения не публиковать обещания.
- Полностью удалить серые предложения из публикации, не маскировать их словами «упоминания бренда». Обучение XRumer/GSA/XEvil, автоматический link spam, искусственный DR, платные ссылки ради ранжирования и Tier схемы не входят в новое коммерческое предложение.

### В. Контроль кода и внешнего вида
- Изменять только минимальный набор Hugo content/templates/config/assets; следить, что общий компонент не ломает иные страницы.
- Проверить Hugo build и фактический generated HTML: 1 H1, Title/description, self canonical, hreflang reciprocal только у существующих эквивалентов, sitemap/robots, schema JSON-LD, корректные internal links/anchors, отсутствие 404-ссылок и старых промо.
- Проверить реальные мобильные/десктопные виды при наличии browser/preview, ориентир 390px и 1280px; доступность и понятный CTA. Если визуальный просмотр не выполнен, явно оставить VISUAL_QA_PENDING.
- Сайт не готов к выпуску, пока не пройдёт `python3 scripts/whitehat_content_gate.py --site public --strict`, и дополнительные crawler/technical/visual QA. Информационный запуск без --strict не даёт release approval.

### Г. Контекст и приёмка
- Каждая страница/системный дефект — отдельный ограниченный коммит, в котором ОБЯЗАТЕЛЬНО обновлён CHATGPT_PROJECT_CONTEXT.md. Контекст указывает исходный/новый URL, пути, интент, SERP evidence, сделанные изменения, точный статус QA, открытые риски, следующий шаг.
- Не смешивать страницу N со страницей N+1 до завершения критичных ошибок N. Проверить GitHub Actions: build + context guard; просмотреть результат после push.
- Не называть готовую страницу «идеальной», если не прошла visual QA, нет SERP в нужной стране, не разрешена миграция, или остались шаблонные/устаревшие ссылки.
- Допустимые статусы: INVENTORIED, SERP_UNVERIFIED, SERP_VERIFIED, EDITED_QA_PENDING, CODE_QA_PASS, VISUAL_QA_PENDING, CONTENT_APPROVED, RELEASE_BLOCKED, READY_FOR_RELEASE. Статус записывать явно и обоснованно.

## 3. Релизные критерии и стоп-условия

Перед публикацией должны быть подтверждены: полный архив/резервная копия исходной версии, точный маршрут каждого старого URL, отсутствие ссылочного спама и неразрешённых коммерческих утверждений, нужные EN/RU/ES страницы, рабочая навигация и 404/410, кросс-языковые canonical/hreflang, валидный sitemap, статус HTML 200 у целевых страниц, доступность, мобильная проверка, производительность (оценка по реальному Lighthouse/CrUX где возможно), отсутствие блокирующих ошибок в CI. Непроверенное не приравнивается к пройденному. Изменение живого сервера только после отдельного явного разрешения владельца.
